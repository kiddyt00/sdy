二、轮次记录

第 1 轮 · 扫码枪商品入库

先厘清概念：「扫码枪商品入库」包含两个含义，共用扫码动作但流程不同——
① 新品建档：商品档案里还没有这条商品 → 扫条码 → 补录信息 → 建立档案；
② 进货收货入库：档案已有 → 扫码登记到货数量 → 库存增加。
下面先做全景梳理，再逐点与你确认。

2.1 入库动作全流程

扫码（枪 / 手机摄像头）→ 后端按条码查档案 →
├─ 有档案 → 录入数量（可连续扫码自动累加）→ 选供应商 / 批次 / 效期 → 确认生成入库单 → 库存增加 → 参与月度对账同步
└─ 无档案 → 进入新品建档：条码自动带出 → 补录 名称 / 类目 / 单位 / 规格 / 进价 / 售价 / 图片 → 保存建档 → 新品反向同步到牵牛花
场景触发核心动作产出与牵牛花关系
新品建档新商品首次到货；或扫码发现档案里没有扫码 → 查无 → 补录信息 → 建档商品档案 +1新品需反向同步到牵牛花
进货收货入库供应商送货到店扫码 → 有档案 → 录数量 → 选供应商/批次 → 确认入库单 + 库存增加入库量计入月度库存同步
盘点核对定期盘点 / 临期检查扫条码核对系统库存差异报告差异人工确认后才同步

2.2 扫码设备怎么选

方案成本说明
手机摄像头（零成本）0 元小程序内 wx.scanCode 直接扫码，MVP 阶段可先顶替
USB 一维枪40～150 元插收银电脑即用，键盘模拟输入
无线一维枪100～250 元仓库/货架走动扫描更方便
无线二维枪 （推荐）200～400 元支持商品码/付款码/混合码，4 人团队可共用
热敏标签打印机200～500 元自制条码贴签、价签、货架签（无条码商品用）

2.3 条码规则（关键前提）

  • 条码 = 商品唯一键（EAN-13）：500ml 和 1L 是两个不同条码，一货一码，同商品不同规格不可共用一个条码。
  • 无条码商品（散装、称重、生鲜、临期拆包）：需要策略——自制内部条码 + 标签打印，或按称重码/件卖处理。
  • 校验与查重：扫码枪读进来是纯数字串，后端要做格式校验、重复条码拦截，避免一码多货。

2.4 与牵牛花的同步关系（沿用主方案已定框架）

已定：建档双向——首次从牵牛花批量迁移（含条码字段，校验 + 差异报告人工确认）；小程序里新建的商品反向同步回牵牛花。入库单数量作为月度库存增量同步的一部分，不实时打通。

2.5 本轮待确认的决策点

决策点选项影响

D2 无条码商品策略自制条码贴签 / 称重码 / 暂不处理决定散装/生鲜能不能入库、要不要买标签打印机

2.6 扫码之后，详细信息从哪来（核心机制）

先破除一个误区：扫码枪只是把条码变成一串数字（键盘模拟输入，如 6901234567892），枪本身不含任何商品信息。所谓「扫一下就有详情」，靠的是软件拿着这串数字去查数据源——数据源里没有，就什么都显示不出来。
扫码（枪 / 手机摄像头）→ 得到条码数字串 → 查「自家商品库」→
├─ 命中 → 返回 名称 / 规格 / 图片 / 价格 / 库存 → 秒出详情
└─ 未命中 →（可选）调外部条码库自动补全候选（名称 / 品牌 / 规格 / 图片）→ 人工核对修改 → 保存建档 → 从此以后该码秒出详情
信息源能提供什么拿不到什么获取方式定位
自家商品库（小程序后台）名称/规格/图片/分类/自家售价/实时库存—（最全）建档时录入（迁移+手工+扫码补录）主力：每次扫码必查
牵牛花迁移档案名称/规格/类目/条码实时库存、自家定价首次月度 CSV 批量导入首批建档的数据底座
外部条码库 API名称/品牌/规格/图片（覆盖国内 69 码为主）价格、库存、自家分类按次调用、低收费「查无商品」自动补候选，人工确认后落库

外部条码库可选来源（已查证）：

  • 阿里云云市场「商品条码查询」API（按次低收费，需实名）：入口1 / 入口2，实践文章见 零售进销存开发：商品条码查询 API 方案实践
  • open.bcpmdata.com 商品条码 API：接口说明
  • 中国物品编码中心（GS1 中国，官方条码源头）：官网有免费条码查询入口，适合人工核对，不适合程序高频调用
  • 淘宝 / 京东开放平台条码接口：需企业资质与类目申请，门槛高，个人开发者一般不用
必须注意：外部条码库数据不全、滞后、甚至有错（一码多品、改名换包装）。所以外部库只能做「自动填候选」+「人工确认」，价格与库存绝不能自动填外部数据——价格用自家定价，库存以自家入库/盘点为准。
D6 已定（用户 m00815 确定）：采用阿里云云市场「商品条码查询」API，设计为本地优先 + 云端兜底 + 回填本地——云端只在「本地两库都未命中」时调用一次，查得结果回填进本地条码库，详见 §2.7。

2.7 设计方案：本地条码库（字典） + 商品库（档案），云端兜底

关键区分（用户 m00832 修正）：本地条码库 ≠ 商品库。
本地条码库（barcode_lib）是「字典层」：条码 → 基础信息（名称/品牌/规格/图片），来自云端查询、迁移或建档沉淀，永久保存，任何扫码先命中它、复用结果、免重复调云端。
商品库（product）是「档案层」：已建档商品的全量档案（自家分类/进价/售价/单位/库存/同步状态）。
两者关系：商品库里的条码必然能在条码库里找到字典项；条码库有字典项但未必已建档。建档 = 从条码库带出基础信息 + 人工补全业务字段 → 写入商品库。
扫码（枪 / 手机）→ 条码数字串 → POST /api/barcode/resolve →
① 查「商品库 product」（条码唯一索引）→ 命中 → 返回完整详情（含价格库存，source=local）→ 结束，永不调云端
② 未命中 → 查「本地条码库 barcode_lib」（字典）
  ├─ 命中 → 返回基础信息 + 「未建档，一键建档」提示（source=lib）→ 不调云端
  ├─ 有「查无」标记（未过期）→ 返回空 + 引导手工建档（source=none）→ 不调云端
  └─ 无记录 → ③ 调云端 API（限频 + 去重锁）
    ├─ 查到 → 写入本地条码库（永久） → 返回基础信息（source=cloud）→ 人工确认 → 建档进商品库
    └─ 查无 → 条码库记「查无」标记（TTL 90 天）→ 引导手工建档

两个库 + 日志的设计：

存储定位关键字段命中即免云端
product 商品库档案层：已建档商品全量条码（唯一索引，关联条码库）/名称/规格/图片/自家分类/进价/售价/单位/库存/牵牛花同步状态✅ 永久
barcode_lib 本地条码库字典层：条码→基础信息，永久沉淀条码（唯一主键）/名称/品牌/规格/图片/来源（cloud·migrate·manual）/状态（normal / not_found）/查无标记有效期（TTL 90 天）✅ 永久（查无标记过期后可重查）
scan_log 扫码日志（可选）运营统计与排查条码/时间/命中层级（product·lib·cloud·none）/操作人—

云端调用节流规则：

  • 三级命中才上云：product → barcode_lib → 云端，前两级命中绝不调云端
  • 同码并发合并：1 秒内同一码只放行 1 次云端调用（后端锁），其余请求直接等结果
  • 全局限速串行：云端请求走串行队列，防止瞬时并发把套餐次数烧完
  • 失败熔断：单次失败重试 1 次；连续失败 5 次熔断当日（转手工建档，次日自动恢复）
  • 用量看板：后台显示「今日云端调用 / 套餐剩余」，建档高峰期可手动暂停云端

与扫码枪 / 手机联动（共用同一接口）：

  • 统一接口 /api/barcode/resolve：扫码枪和手机扫码都调它，业务逻辑完全一致，枪零配置（键盘模拟，无需驱动）
  • 扫码枪（电脑后台）：入库/建档页面输入框聚焦 → 枪扫入数字串 → 页面即时返回详情或字典候选 → 一键确认建档
  • 手机（小程序）：wx.scanCode 拿码 → 调同一接口 → 展示详情/候选 → 确认建档

建档闭环与成本账：

  • 字典候选确认 → 建档进商品库（自家分类/进价/售价/单位可改、图片可换）→ 新品进「待同步」队列，月度反向同步牵牛花
  • 云端只在「两库都未命中」扣次数：建档期把 2000+ SKU 扫一遍后，日常新增品极少，云端月调用量趋近于 0
  • 套餐建议：先买小次数套餐跑通流程（购买页实际价格/次数为准），建档完成后再按需扩容；整块预算可控制在几百元内
红线：云端返回的名称/规格可能错（一码多品、换包装），字典可自动沉淀复用，但建档进商品库必须人工确认；价格与库存永不自动填云端值——价格用自家定价，库存以自家入库/盘点为准；扫码只读不改库存——库存一律手动调整（D8）。
最终效果：同一支枪/手机，第一次遇到新码多一步「核对→确认建档」，之后所有码秒出详情、零云端成本——条码库（字典）越用越厚，商品库（档案）越建越全。

2.8 扫码枪交互设计与采购（用户 m00859 提问）

交互方式结论（建议方案）：「2.4G 无线（USB 接收器）」为主 + 「USB 有线」备用。
关键认识：扫码枪对系统来说就是一个「键盘」——它把条码数字串 + 回车直接打进输入框，零驱动、零配置、天然适配网页后台，不需要任何枪端开发；「适配我们的系统」的工作全部在我们自己前端（见下方清单），与枪的品牌型号无关。

三种连接方式对比：

方式原理优点缺点适用场景
USB 有线（键盘模拟）插线即键盘最便宜 40–150 元、免充电、零延迟线缆束缚固定台（建档/收银/打包）
2.4G 无线（USB 接收器）枪 ↔ 接收器私有 2.4G，接收器插电脑当键盘无束缚、免配对、距离 30–50 米、充电底座接收器占一个 USB 口★ 仓库/拣货/盘点（推荐主力）
蓝牙（HID / SPP）蓝牙键盘模式，或串口模式可连手机/平板需配对、重连偶尔丢码、SPP 要写串口程序、电量管理手机端场景（但我们手机端用摄像头扫码，免费，用不到）

为什么不用蓝牙为主：

  • 蓝牙 HID 连手机要求输入框有焦点且一次只配对一台设备；我们手机端已有 wx.scanCode 摄像头扫码（零成本），桌面端用 2.4G 更稳定
  • 蓝牙只适合「没有 USB 接收器、又偏要用枪扫」的极少数场景，不作为主方案

与系统交互的具体设计（我们系统侧要做的事）：

  • 全局「扫码台」：后台任一页面按快捷键（如 F2 或右上角扫码图标）弹出扫码输入框，始终保持监听
  • 枪扫入数字串 + 回车 → 前端捕获 Enter → 调 /api/barcode/resolve（与手机完全同一接口）
  • 结果卡片：商品库详情 / 条码库字典 +「一键建档」/ 云端候选确认 / 查无引导手工建档（对应 §2.7 三级链路）
  • 防重复与连扫：同一码 1 秒内只触发一次；连续扫描自动追加成列表（批量建档/盘点用）——枪每扫一码自动回车，天然支持连扫，无需特殊协议
  • 枪端可配置（用说明书里的配置码扫一下即可，无需开发）：默认后缀「回车」已满足；需要时加前缀区分来源、调整字符间隔、关声音等

二次开发 / 适配性（用户关心点）：

  • 不需要厂商 SDK：键盘模拟（HID）模式下任何品牌扫码枪都即插即用，不存在「适配我们系统」的开发问题
  • 未来若要做枪端高级功能（枪上按键自定义触发动作、蓝牙多枪同连管理、批量上传模式），新大陆/霍尼韦尔/斑马等提供 SDK——但这是升级项，MVP 不需要

采购建议（符合主方案硬件预算 500–900 元）：

  • 1 台 2.4G 无线 2D 扫码枪（仓库/拣货/盘点主力）——200–400 元
  • 1 台 USB 有线 2D（固定建档/收银台，可选，先用无线那把也够）——150–350 元
  • 品牌参考：汉印、新大陆、得力、霍尼韦尔（贵）；选 2D 款：能读屏幕码/破损码/电子价签二维码，比 1D 耐造、兼容未来场景
D7 已定（用户确认）：先不买枪——MVP 阶段全部用手机摄像头扫码（wx.scanCode）验证流程，流程跑通后再按需采购；届时按「2.4G 无线 2D 为主 + USB 有线备用」组合执行（见上方采购建议）。
