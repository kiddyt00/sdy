## 一、微信支付（小程序 JSAPI）· 本轮做

### 1.1 目标

顾客在小程序里下单后**必须当场付掉**才进入备货流程；支付走微信支付 v3 JSAPI，服务端只用 Go 标准库（`crypto/rsa`、`crypto/aes`、`crypto/cipher`），**不新增任何依赖**。

### 1.2 环境变量（只从环境读，绝不入库、绝不进日志）

| 变量 | 说明 |
| --- | --- |
| `WXPAY_MCHID` | 商户号 |
| `WXPAY_SERIAL_NO` | 商户 API 证书序列号 |
| `WXPAY_PRIVATE_KEY_PATH` | 商户私钥 `apiclient_key.pem` 路径（服务器 `/root/sdy/secrets/`） |
| `WXPAY_API_V3_KEY` | APIv3 密钥（32 位），用于回调 AES-256-GCM 解密 |
| `WXPAY_PLATFORM_CERT_PATH` | 微信支付平台证书 / 微信支付公钥 PEM（**必须手动下载放置**，服务端不会向 `/v3/certificates` 自动拉取；缺失即支付未开通） |
| `WXPAY_API_BASE` | 默认 `https://api.mch.weixin.qq.com`，可注入假支付服务（测试用） |
| `WXPAY_NOTIFY_URL` | 默认 `https://mall.shadouyou.cloud/api/pay/notify` |

**未配置完整** → 支付不可用：`POST /api/pay/prepay` 返回 503 `{"error":"微信支付未配置（服务端缺少商户号 / 证书 / APIv3 密钥）"}`；**下单接口照旧可用**（`paid=0`），本地开发与验收脚本不受影响。

### 1.3 金额一律整数分

`amountFen(total float64) int64 = int64(math.Round(total*100))`。库里仍存 REAL 元（不改列类型），但**所有支付相关计算与核对都用分**：下单金额、回调核对、退款金额。回调金额与订单不一致 → 拒绝处理并记日志（**绝不按回调金额改单**）。

### 1.4 订单新列（全部走 `ensureColumn` 补列；索引必须进 `postMigrateStmts`）

`openid TEXT NOT NULL DEFAULT ''`、`paid INTEGER NOT NULL DEFAULT 0`、`paid_at TEXT NOT NULL DEFAULT ''`、`transaction_id TEXT NOT NULL DEFAULT ''`、`prepay_id TEXT NOT NULL DEFAULT ''`、`pay_expire_at INTEGER NOT NULL DEFAULT 0`（Unix 秒）、`refund_id TEXT NOT NULL DEFAULT ''`、`refund_state TEXT NOT NULL DEFAULT ''`（`''`/`processing`/`success`/`fail`）、`refund_at TEXT NOT NULL DEFAULT ''`。

新索引（放进 `postMigrateStmts`，理由见第 27 轮生产事故）：
- `CREATE UNIQUE INDEX IF NOT EXISTS idx_orders_transaction ON orders(transaction_id) WHERE transaction_id<>''`（回调幂等的最后一道闸）
- `CREATE INDEX IF NOT EXISTS idx_orders_pay_expire ON orders(paid, pay_expire_at)`（超时扫单）

`Order` 结构体加同名 JSON 字段：`paid`、`paidAt`、`transactionId`、`payExpireAt`、`refundId`、`refundState`。**`openid` 不进 JSON**（避免泄露他人微信号；顾客端只需要知道自己的单）。

**老库一次性回填（必须做，否则升级当天砸老板的备货队列）**：`paid` 列是补出来的、默认 `0`，而支付上线前就存在的 `pending` 老单当时根本没有线上支付这回事——它们本来就在备货队列里、也可能是现金收的。不回填的话升级后这些单会被「待备货队列只列已付款」踢出去，顾客那边还会看到「待付款」和倒计时。

所以：补列时用能报「本次是否真的新增了这一列」的 `ensureColumnAdded(...) (added bool, err error)`（内部仍走 `PRAGMA table_info`）；**当 `paid` 属于本次新增**（即首次升级到 0.9.0 的老库）时，在迁移里执行一次：

```sql
UPDATE orders
   SET paid = 1,
       paid_at = CASE WHEN paid_at = '' THEN created_at ELSE paid_at END
 WHERE paid = 0 AND status <> 'cancelled';
```

- `paid_at` 用 `created_at` 是为了**不污染「今日已收款」**（否则升级当天把历史单全算成今天的收款）。
- `pay_expire_at` 保持 `0`：扫单条件是 `pay_expire_at>0`，所以扫单不会碰这些老单。
- 已取消的老单不回填（`paid=0`，不影响任何展示与队列）。
- **绝不能写成无条件 UPDATE**：那样每次重启都会把当天未付款单刷成已付款，等于白拿货。
- 新库（表本来就是新列的）没有行，回填天然是空操作；升级后新建的单照旧 `paid=0`。

### 1.5 HTTP 契约

- `POST /api/pay/prepay`（顾客；身份照第 27 轮 `identityOf`）
  入参 `{"orderId":"M…"}`。校验：订单存在、**归属本人**（管理员/员工放行）、`status='pending'`、`paid=0`；未超时。返回 `{"outTradeNo":"M…","amountFen":600,"payParams":{"timeStamp":"…","nonceStr":"…","package":"prepay_id=…","signType":"RSA","paySign":"…"},"expireAt":1791969999}`。
  幂等：同单已存在未过期 `prepay_id` 直接复用（不重复下单）；过期则重新下单。`out_trade_no` = 订单号（**绝不带毫秒**）。
  **跨端补 openid（网页下单 → 小程序支付）**：若订单 `openid=''` 且订单手机号 == 身份手机号 → 先把当前身份的 openid 补写进订单再继续（网页下单的顾客能在小程序里付同一单）；订单手机号 ≠ 身份手机号 → 403 `这个订单不是你的，无法支付`；身份只有手机号、没有 openid（纯网页身份）→ 400 `请在微信小程序里登录后再支付`；订单无 openid 且顾客换过手机号 → 提示 `这单是网页下单的，请用下单时的手机号登录小程序支付`（后台可用 `标记已收款` 兜底）。
- `POST /api/pay/notify`（**公开**，无身份）
  验签（`Wechatpay-Timestamp/Nonce/Signature/Serial` + 平台证书，用 `hmac.Equal` 级别的常量时间比较）→ AES-256-GCM 解密（AAD = `associated_data`）→ 校验 `mchid`、`appid`、`out_trade_no` 存在、`amount.total` == 订单分、`trade_state=='SUCCESS'` → 事务内幂等置 `paid=1`/`paid_at`/`transaction_id`（`transaction_id` 唯一索引兜底）。
  成功必须回 `HTTP 200 {"code":"SUCCESS","message":"成功"}`；**业务校验失败回 4xx（让微信重试）而不是 500**；重复回调（同一 `transaction_id`）直接回 SUCCESS，不改动任何数据。**任何情况都不因业务错误 panic。**
- `POST /api/pay/refund-notify`（**公开**，同上验签解密）：按 `out_refund_no`（= 订单号，或 `R+订单号`）找到订单，更新 `refund_state`/`refund_id`/`refund_at`；幂等。
- `GET /api/pay/status?orderId=M…`（顾客，归属校验）：本地已 `paid=1` 直接返回；本地未付且距上次查单 > 30 秒 → **主动查单兜底**（`GET /v3/pay/transactions/out-trade-no/{no}?mchid=`），命中 `SUCCESS` 就落库。返回 `{"paid":true,"status":"pending","transactionId":"…","refundState":"","expireAt":…}`。
- `POST /api/orders/{id}/mark-paid`（管理员/员工，`adminGate`）：线下收款/未开通支付时的兜底，置 `paid=1`、`paid_at`，可带 `{"note":"现金"}`；**不写 stock_log**。
- `GET /api/orders` 新增筛选 `paid=0|1`（`OrderFilter` 扩展），顾客身份下照旧只能筛自己的单。
- `GET /api/settings` **新增派生字段 `payEnabled`（严格布尔）**，值＝`pay != nil && pay.ready()`。实现用**嵌入结构体**（`type settingsResp struct { store.Settings; PayEnabled bool \`json:"payEnabled"\` }`），既有 8 个平铺键（`name`/`phone`/`address`/`footer`/`lowStock`/`minOrder`/`deliveryFee`/`minFree`）一个都不动。三端口径一致：**只有显式 `true` 才算开通**，字段缺失 / 请求失败 / `'true'` / `1` 一律按**未开通**。

### 1.6 超时未付自动取消

`store.CancelExpiredUnpaid(nowUnix int64, limit int) (int, error)`：事务内取 `paid=0 AND status='pending' AND pay_expire_at>0 AND pay_expire_at<=now` 的单，逐单 `status='cancelled'`、`updated_at` 刷新、**回补库存**、写 `stock_log`（`kind='pay_timeout'`、`reason='超时未付自动取消'`、`order_id` 回填，商品已删则 delta=0 留痕不失败），幂等（已 cancelled 的不再处理）。
`main.go` 起一个 goroutine：每 60 秒跑一次，`limit=50`；只在真的取消了单时打日志；`context` 取消时退出。**双容器同时跑是安全的**（事务 + 状态判定 + 幂等），但必须在报告里写明这一结论。
测试钩子（只为验收，默认值不变）：`PAY_EXPIRE_SECONDS`（默认 900）、`PAY_SWEEP_INTERVAL`（默认 `60s`，支持 `1s`/`500ms`，非法值回退默认）。`deploy/accept-pay.js` 用短值起临时后端来真验「到期自动取消 + 库存回补」。

**未开通支付时绝不允许设超时窗（上线前必修的真实缺陷）**：建单**只在支付可用时**才算 `pay_expire_at`——
`CreateOrder` 里 `var expireAt int64; if in.PayWindow { expireAt = now + PayExpireSeconds() }`（`PayWindow bool \`json:"-"\`` 由 `cmd/server` 在建单处传 `pay != nil && pay.ready()`）。为假时写 **0**；而候选条件本就要求 `pay_expire_at>0`，故 0 ＝ 永不被扫。
同时扫单 goroutine 每 tick 先 `if pay == nil || !pay.ready() { continue }`（**双保险**：库里残留的 `pay_expire_at>0` 老单在未开通时也不会被误杀）。
反例（修复前的行为，禁止回归）：未开通时给正常单写 `now+900`，15 分钟后扫单把单取消并回补库存（`kind='pay_timeout'`），叠加「未付款不进备货队列」→ 备货队列恒空、**店铺停摆**。
回归锁：`TestPayWindowNoCountdownWithoutPay`、`TestPayOrderNoCountdownWhenPayOff`、`TestPaySettingsPayEnabled`、`TestPaySweepGoroutine`（三阶段：pay=nil 不取消 → pay 就绪才取消 → ctx 取消即退出），以及端到端 `deploy/accept-pay-off.js`。

### 1.7 退款

取消**已付款**订单（顾客取消 / 后台取消 / 员工操作）→ 订单 `status='cancelled'` + 调退款接口（`out_refund_no` = `R` + 订单号，金额 = 订单分，原因 = 取消原因）→ `refund_state='processing'`；退款结果由 `refund-notify` 或 `GET /api/pay/status` 的退款查询兜底更新为 `success`/`fail`。**未付款订单取消不调退款**。退款失败必须在后台可见（红字），不许静默。
**未开通支付时**取消已付款单：取消**仍然成功**（不能因为支付没开通就禁止取消），但 `refund_state` 置 **`fail`**（不许留空骗人），文案「微信支付未配置，无法自动退款（请到微信商户平台手工退款）」——钱要老板去商户平台手工退，系统如实说。

### 1.8 界面（三端状态文案仍逐字一致，**不新增 status 值**）

派生显示：`pending + paid=0` → 显示「待付款」；`pending + paid=1` → 「待备货」；其余按第 27 轮文案不变。
**但这一条只在支付已开通时成立**：`payEnabled !== true` 时，三端必须**退回第 28 轮语义**——`pending` 单显示「待备货」、进备货队列、后台「待收款」计数 `toCollect=0`、不给「去支付」入口（只给「取消」），顾客端下单后**不进收银台**而是直接「下单成功」。店铺在支付未开通时照常运转，是硬要求。
- 小程序：下单成功 → 直接进 **收银台**（新页 `pages/pay/pay`，金额、商品数、待付倒计时、`去支付`）→ 成功后显示「支付成功，正在备货」+ `查看订单`；失败/取消留在收银台可重试。「我的订单」里待付款单显示 `去支付` + 剩余时间，超时显示「已取消（超时未付）」。
- 小程序：**未登录（无 openid）不允许下单**（支付需要 openid），提示「请先用微信登录，下单后可直接支付」。
- 管理后台：订单列表新增「支付」列（未付款 / 已付款+时间 / 退款中 / 已退款）、筛选「支付状态」、订单详情显示微信支付单号与退款号、「发起退款」按钮（二次确认）；**「待备货」队列与 KPI 只统计已付款单**；「待收款」单独计数；概览新增「今日已收款（微信）」= **按付款时间 `paidAt` 归日**（取不到才退回 `createdAt`）且 `paid=1 && status<>'cancelled'` 的合计——必须与微信商户账单口径一致（昨晚下单、今天付款的钱算今天）。「今日待收款」「今日营业额」仍按 `createdAt` 归日，页面上要写清两种口径的差别。
- Web 商城端：**本轮不做线上支付**（需要 Native/H5 支付权限），如实披露；Web 下单成功后提示「请在小程序里用微信支付」并给小程序码。网页订单在小程序里**用同一个手机号登录后可以直接支付**（见 1.5 跨端补 openid），所以「所有订单都必须先线上付」这条在网页入口也成立。

### 1.11 上线操作清单（拿到商户资料后按此做，缺任一项＝支付关闭，不会半开）

需要老板提供（**只在服务器上放，不要贴进聊天、不要进仓库**）：

| 项 | 从哪来 | 放哪 |
| --- | --- | --- |
| 商户号 `WXPAY_MCHID` | 微信商户平台首页 | 服务器 `/root/sdy/.env` |
| 商户 API 证书序列号 `WXPAY_SERIAL_NO`（40 位十六进制） | 商户平台「账户中心 → API 安全」 | 同上 |
| APIv3 密钥 `WXPAY_API_V3_KEY`（32 位） | 同上（需自己设置） | 同上 |
| 商户 API 私钥 `apiclient_key.pem` | 商户平台下载的证书包 | 服务器 `/root/sdy/secrets/apiclient_key.pem` |
| 微信支付平台证书 / 微信支付公钥 | 商户平台「账户中心 → API 安全」下载（代码不会自动拉取，必须手动放置） | 服务器 `/root/sdy/secrets/wechatpay_platform_cert.pem` |

服务器上的四条命令：

```bash
cd /root/sdy
mkdir -p secrets && chown 10001:10001 secrets && chmod 700 secrets
# 把两个 pem 放进 secrets/ 后：
chown 10001:10001 secrets/*.pem && chmod 600 secrets/*.pem
# .env 里补齐（路径必须是**容器内路径**）：
#   WXPAY_PRIVATE_KEY_PATH=/app/secrets/apiclient_key.pem
#   WXPAY_PLATFORM_CERT_PATH=/app/secrets/wechatpay_platform_cert.pem
#   WXPAY_NOTIFY_URL=https://mall.shadouyou.cloud/api/pay/notify
#   WXPAY_API_BASE=            # 留空＝正式域名 https://api.mch.weixin.qq.com
./deploy/rolling-update.sh && curl -s http://127.0.0.1:8093/healthz
bash deploy/pay-check.sh            # 体检（只读，不重启）：逐项查序列号 40 位 / APIv3 密钥 32 字节 /
                                    #   pem 是否存在且 600、路径是否是容器内 /app/secrets/…、
                                    #   探一笔 prepay 判断「已开通 / 未开通」，并打印容器里的支付日志线索
```

体检脚本 `deploy/pay-check.sh` 的设计口径：**不打印任何密钥原文**（只显示长度与首尾两位）；发现配置错误退 `1`；配置干净但支付未开通退 `0`（未开通是正常状态，不是故障）。任何一项拿不准时先跑它，别靠肉眼核 40 位十六进制。

上线后自检 5 条：① 小程序下一笔最小金额单 → 拉起收银台并付款成功；② 后台「今日已收款」出现该笔、微信商户平台账单对得上；③ 支付成功前后台「待备货」看不到这单，支付成功后出现；④ 挂 16 分钟不付款 → 订单变「已取消（超时未付）」且库存回补；⑤ 取消一笔已付款单 → 微信商户平台出现全额退款、「退款单号」与退款状态在后台可见。

**未配置时要如实说明**：`WXPAY_*` 缺任一项 → `POST /api/pay/prepay` 返回 503（小程序提示「店里还没开通在线支付，请联系店家」），下单、备货、打印全都不受影响，订单状态为「待付款」。这属于「支付未开通」，**不是**故障。
