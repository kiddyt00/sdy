# 批发订货小程序 · 产品说明（2026-10-15 定型）

> **这份文档是给老板看的**：全篇不出现技术名词，每一条都写成「顾客会看到什么、店里要做什么」。
> 技术口径与实现细节在 `README.md` / `server/README.md` / `.agent_rules.md`，不在本文。
>
> **为什么要重写这一页**：原来做的是「小区即时零售」——顾客下单、30 分钟送到家。现在改成了
> 「**批发商订货**」——顾客是来进货的店主，货由我们自己送。定位一变，**卖的节奏、顾客的动线、
> 该先做什么，全都跟着变**。这份文档把变化摊开，供老板逐条确认或推翻。

---

## 一、一句话说清卖的是什么

| | 原来是（即时零售） | 现在是（批发订货） |
| --- | --- | --- |
| 顾客是谁 | 周边居民，买一两件应急 | **开店的老板**，进一周的货 |
| 一次买多少 | 1–3 件 | **整箱、整提**，一单几十件 |
| 多久要货 | 30 分钟送到 | **当天或隔天送到就行** |
| 谁送 | 送货上门（3 元配送费） | **我们自己送**（没有第三方跑腿） |
| 怎么付 | 每单线上付 | 线上付为主，**批发老惯例还有挂账月结** |

**一句话**：以前是「顾客点一份可乐，半小时到手」；现在是「隔壁饭店老板订 20 箱可乐，明天上午送到」。

## 二、顾客（店主）会怎么用

这是**我们猜测**的动线，请老板拿它去跟店里真实的订货老板对一遍——**猜错了要改的就是这里**：

1. **第一次来**：扫码进小程序 → 填一次手机号（这一步同时认出他是哪家店）→ 看到**自己的批发价**
2. **平时进货**：翻「常购清单」→ 改数量 → 下单（**不是**每次从首页一件件翻）
3. **遇到新品**：搜名字或扫码 → 看到自己的价和库存 → 加进去
4. **下单后**：选**送货**（地址是店址）→ 线上付款 或 记账
5. **等货**：想知道「货到哪了」→ 看到「**已出发 / 快到 / 到门口了**」这类状态
6. **收货**：确认收到
7. **月底**：对一次账（挂账的部分要能看清「这月一共欠多少、哪几笔」）

**关键判断**：第 2 步（常购清单）和第 7 步（对账）**现在都没有**。如果老板确认「订货老板就是这样进货的」，这两件事的优先级应该排在实时轨迹**之前**。

## 三、现在已经有的（可直接用）

| 能力 | 说明（顾客视角） |
| --- | --- |
| **按店给价** | 每家店填过一次手机号，之后看到的就是**自己的批发价**，不是零售价 |
| 商品浏览 / 搜索 / 分类 / 热销 | 顾客能找到货 |
| 扫码找货 | 拿起一样货扫条码，直接跳出这件货 |
| 购物车 / 下单 / 订单查询 | 下单全流程 |
| **线上付款（微信支付）** | 下单后当场付掉；没付钱的单不会送到备货队列 |
| 取消订单 / 自动退款 | 付过钱后取消，钱自动退回去 |
| 已取消单的库存自动回补 | 取消不会把库存算错 |
| 后台管货 | 老板建档、改价、改库存、上下架、看报表、导 CSV |
| 送货状态（粗粒度） | 「待处理 / 配送中 / 待自提 / 已完成 / 已取消」五种状态 |

> **注意**：上面这些**大部分第 19–28 轮就做好了**，「按店给价」这套正是为批发准备的，
> 与今天的定位严丝合缝，不用重做。

## 四、批发订货真正需要、但现在缺的

按「对订货老板的痛感」排序（**请老板重新排**，这份排序是我猜的）：

| # | 缺什么 | 不做的后果 | 工作量 |
| --- | --- | --- | --- |
| 1 | **整箱 / 整件换算** | 现在只能按「瓶/罐」下单，进货要买 24 瓶得点 24 次；**批发单最容易卡在这里** | 中 |
| 2 | **常购清单一键下单** | 老顾客每次都得从头翻一遍，宁可打电话 | 中 |
| 3 | **挂账 / 月结** | 批发老惯例是先拿货月结，只支持线上付款会挡住一部分老客户 | 中大 |
| 4 | **阶梯价**（多买更便宜） | 现在一个商品只有一个批发价，买的量多也没优惠 | 中 |
| 5 | **送货进度**（已出发 / 快到 / 到门口） | 订货老板反复打电话问「货到哪了」 | 小 |
| 6 | **实时位置**（地图上一个点） | 锦上添花，量少就不值得做 | 小–中 |

**老板要做的判断**：把 1–6 按「对你生意的影响」重新排一次。我猜的顺序不一定对——
**只有你知道哪条最疼**。

## 五、实时轨迹这件事（老板问过，单独说清）

### 能做，但有一条物理限制

「送货员现在在哪」，**能做**。但有件事必须先讲明白：

> 送货员的手机小程序**退到后台（接电话、回微信、锁屏），位置上报就会停**。
> 想让它不停，需要微信后台特批「后台持续定位」——**这个基本只有美团、滴滴这类平台才批得下来**，
> 我们这种自营商城申请不下来。

**这意味着**：全程实时轨迹，只有在「**送货员把小程序一直开在屏幕上**」时才成立。

### 两条路，代价差很多

| | **做法一：粗粒度状态**（推荐先做） | **做法二：地图实时位置**（老板已选） |
| --- | --- | --- |
| 顾客看到 | 「已出发」→「大概还有 20 分钟」→「到门口了」 | 地图上**一个点**在动 + 「最近更新时间」 |
| 送货员要做什么 | 出发时点一下、到门口点一下 | **全程开着小程序**（否则点不动） |
| 手机耗电 | 几乎不耗电 | 明显耗电 |
| 技术风险 | 低 | 中：定位不准、信号差会跳 |
| 什么时候做 | 对账、常购清单之后 | 老板已拍板先做这个 |

**做法二的具体形态**（老板已选 A 档）：
- 顾客在订单页看到一张地图，上面一个标记 = 送货员当前位置
- 旁边写「最近一次更新：2 分钟前」——**这个时间必须显示**，否则顾客会拿一个 10 分钟前的旧位置当实时
- 送货员端多一个「**开始送货**」开关：**点了才开始上报**，不点就不上报（既省电，也避免店员下班后位置还在传）
- 地图与「点开地图导航」是**微信内置能力，不用另外买**，没有年费

### 一个要老板想清楚的点

批发订货的顾客**是店主，不是点外卖的人**。店主真正关心的是「**货几点能到**」，
而不是「骑手现在骑到哪条街」。所以做法一（三句话）往往比做法二更解决问题，而且几乎不耗电。

**这是老板已经做过的选择**（选了做法二 A 档），我把它如实记在这里——
如果后面发现「顾客其实只想知道几点到」，随时可以退回做法一，做法二的点也能复用。

## 六、作废的东西（不再做，避免白干）

| 作废 | 原因 |
| --- | --- |
| **第三方跑腿平台接入** | 定位是「都是自己送」，不需要达达/顺丰同城/闪送/UU/美团 |
| 订单「自己送 / 第三方送」标记 | 只有自己送一种，标记是多余的 |
| 原「即时零售」的送达承诺 | 30 分钟送达 / 3 元配送费 / 满 30 免运费，是零售场景的定价，批发不适用 |
| 顾客端「送货上门」的零售调性文案 | 批发场景要改成「送货 / 自提」，并把送货默认选上 |

> 对应的代码与文档改动，等老板确认本页后再动手（现在只写说明，不改代码）。

## 七、请老板确认的 5 件事

逐条打勾或改字即可，**不确定就写「不确定」**，我再拆成更小的问题：

1. **顾客动线对不对？**（第二节那 7 步）—— 哪一步跟你想的不一样？

5. **零售的散客还接吗？** 如果以后只服务订货的店，顾客端的「一件也能买」和 3 元配送费就可以去掉。

## 八、附：这份定型带来的取舍

**保留**：手机号即身份（不用注册）、按店给价、全流程线上付款、购物车、扫码找货、后台管货。

**明确不做**（除非老板要）：
- 第三方跑腿
- 顾客自助注册与审核（现在还是店里登记等级）
- 配送员实时轨迹的「历史回放」（批发场景没用）

**技术备注**（给工程看，老板可跳过）：位置能力用 `wx.getLocation` 单次上报 +
`<map>` 组件展示，不申请后台持续定位；报送频率与「开始送货」开关一起设计；
地图与导航用微信内置能力，不引入腾讯位置服务 key。
