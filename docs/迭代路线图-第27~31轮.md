## 一、现状诊断（六路审计共识）

**顾客端是「功能齐、但不可信」**：页面与动线已经覆盖逛-选-加购-结算-下单-查单-再来一单，问题集中在三处：

1. **状态模型缺「错误」这一维**（最严重）。请求失败被渲染成「空数据」：首页说「没货」、订单页说「没订单」、地址页说「没地址」。顾客看到的是与事实相反的结论，而且**没有任何重试入口**。三端同病（小程序 5 页、Web 商城、后台关键面板）。
2. **身份与归属缺失，导致越权与隐私泄露**（合规级）。
   - `GET /api/orders` 无身份过滤 → 顾客端（小程序 + Web）把**全店订单**的姓名/手机号/门牌号渲染成「我的订单」（`miniprogram/pages/orders/orders.js:49`、`web/index.html:644-666`）。
   - `POST /api/orders/{id}/advance` 无归属校验 → 任意人可推进/完成别人的订单。
   - 地址簿以手机号为钥匙（`GET /api/addresses?phone=`）→ 填别人手机号即可读出对方收货人姓名与完整地址（`store.go:1571-1575`）。
   - 34 个后端端点里 **32 个无鉴权**（含改价 `POST /api/products`、删货 `DELETE /api/products/{code}`、改库存、改角色 `POST /api/wx/role` 可自助提权成员工）。
3. **同一规则四份拷贝，已经算出不同的钱**。配送费免运费门槛：Go 不取整、Web/小程序先 `round2` → 29.995 ≤ 金额 < 30 时 **Go 收 3 元、Web/小程序显示免运费**；未知配送方式 Go 400 / Web 抛错 / 小程序静默 0 元；`minFree=0` 三端三种解释；状态文案 Web「待备货」vs 小程序「待处理」。规则散落在 `server/internal/pricing`、`web/pricing.js`、`miniprogram/utils/rules.js`、`web/mall.js:24-34` 四处。

**后台是「老板真正干活的地方，但会骗他」**：
- 派单失败仍提示「订单进入配送中」（`admin.html:709-717` catch 后没 return）→ 老板以为派了单，实际没派。
- 批量改价/改分类静默把批发价清零（三条批量 payload 都不带 `wholesalePrice`；弹窗批发价永远为空）→ 批发顾客直接按零售价买。
- 后端空响应时静默沿用本地演示值（配送员 `['老张','小李','阿强','小美']`、店名 `'家庭超市'`、库存流水）→ 小票打假店名，派单下拉出现不存在的人。
- 「今日营业额」把未完成订单计入（无在线支付，下单≠收款）→ 高估当天流水。
- 批量操作区藏在折叠面板里（勾选在下、按钮在上）、10 列表格手机横滚、盘点每商品 3 行输入、**零 CSV 导出**、日报只有 32 字宽纯文本、新订单零提醒、危险操作（下架/改数/盘点/确认完成）无二次确认。

**视觉不统一但结构不差**：48 个色值、22 档字号（最低 20rpx，低于 24rpx 可读下限）、4 档圆角、5 种间距；`app.wxss` 的 80+ 设计变量**页面零消费**（全写死 hex）；对比度多处不达标（`#9ca3af` 当正文 30 处 = 2.3–2.5:1；首页/我的渐变右端白字 2.0–2.3:1；购物车禁用按钮 2.54:1）；首页 `.more` + `.page` 叠加出 340rpx 尾部空白；`tabBar` 只有文字没有图标。图片容器都已固定尺寸（无 CLS 问题）——这一块底子是好的，只需接线。

**三端割裂**：小程序有搜索历史/热词/扫码/员工工作台，Web 有键盘与宽屏但下单假成功（离线 toast「本地演示（未入库）」顾客会当成功）、地址簿可越权、420px 横向溢出 143px、`aria/role/tabindex` 计数为 0；后台与员工端职责重叠（扫码入库其实手机更顺手）。

## 二、五轮路线图

每轮都覆盖 **小程序顾客端 + Web 商城端 + 管理后台 + Go 后端**，都要求：补齐测试 → 三端可验证验收 → 上传开发版 → 生产部署 → 文档与提交推送。

### 第 27 轮（0.6.0）· 买得完、看得对 —— 正确性与身份底座
> 目标：顾客不会再看到「别人的订单」，不会再看到「假的没货」，不会再被「假的成功」骗；金额三端算得一模一样。

- **后端**：订单归属过滤（员工令牌=全量 / openid / phone）+ `advance` 仅员工；地址簿能力令牌（`key`）；下单幂等（`clientToken` 唯一索引）+ 库存原子扣减（`WHERE stock>=?`）+ 取消回补写流水；配送费口径与状态文案收敛；`GET /api/settings` 下发 `lowStock/minOrder`；起送价校验；`total` 语义修正；分页 `limit/offset`；管理端鉴权通道（默认关，`ADMIN_PASSWORD` 未设=放行+WARN）。
- **小程序**：错误态与「重新加载」（5 页）；加购角标 3 处漏同步；离线下单不跳转；「立即购买」二次确认；结算条件数 + 自提显示门店地址电话；购物车数量上限=库存、失效商品分组清理；搜索结果加购 + 库存/缺货；订单/地址带 `openid`；低库存「仅剩 N 件」。
- **Web 商城**：离线常驻降级提示 + 提交按钮禁用 + 成功/未提交视觉区分（不再假成功）；空商品库不重播种；订单/地址带身份；420px 溢出与热区/对比度；`label for` + 键盘可达；下单成功统一跳转。
- **管理后台**：派单失败不误报（补 `return`）；批量清空批发价修复；空响应不回落演示数据；今日营业额口径；危险操作二次确认；订单备注展示位。

## 四、第 27 轮接口契约（实现方以此为准）

身份解析优先级（所有订单/地址接口统一）：**管理员 > 有效 `X-Staff-Token`（员工=全量）> `openid`（小程序顾客，服务端用 `wx_user.phone` 解析）> `phone`（Web 顾客，兼容路径）> 无身份 = 400**。

「管理员」= ① `ADMIN_PASSWORD` 未设置（灰度关闭，一律放行 + WARN 一次），或 ② 已设置且请求带**有效管理员 Cookie**。第 ① / ② 条必须与 `requireAdmin` 共用同一个校验函数（`adminOK(r) bool`），不得各写一份——否则开着鉴权时后台自己的订单列表会 400。

| 端点 | 变更 | 规则 |
|---|---|---|
| `GET /api/orders` | 身份过滤 + 分页 | 员工→全量；否则须 `openid` 或 `phone`，仅返回该顾客订单；都没有→400 `{"error":"缺少身份：顾客请带 openid/phone，员工请带 X-Staff-Token"}`；`total`=符合条件总数；新增 `limit`(默认 50/最大 200)、`offset` |
| `GET /api/orders/{id}` | 归属校验 | 顾客身份与订单不匹配→404 `{"error":"订单不存在"}`（不泄露存在性）；员工放行 |
| `POST /api/orders/{id}/cancel` | 归属 | 顾客须匹配；员工放行；回补必须写 `stock_log`（`RowsAffected=0` 记日志不失败） |
| `POST /api/orders/{id}/advance` | 仅员工 | 无有效令牌→403 `{"error":"只有店主可以推进订单状态"}` |
| `POST /api/orders` | 幂等 + 原子 + 起送价 | body 增 `clientToken`（重复提交返回原单，`duplicated:true`，不重复扣库存）；扣减 `UPDATE product SET stock=stock-? WHERE code=? AND stock>=?`，任一行 0 行→整单回滚 400 `{"error":"库存不足：<名称>（还剩 N 件）"}`；`goods < minOrder`→400 `{"error":"还差 X 元起送"}`（`minOrder=0` 不限） |
| `GET /api/addresses` | 能力令牌 | 员工→按 `phone` 查；顾客须 `phone`+`key`（首次保存地址时服务端生成 32 位 hex 并随 `POST /api/addresses` 响应 `{ok:true,key}` 返回，客户端存本地）；缺失/不匹配→`{items:[],total:0}` 静默空 |
| `POST/DELETE /api/addresses` | 同上 | 删除须 `phone`+`key` 或员工令牌 |
| `GET /api/settings` | 运营参数下发 | 新增 `lowStock`(默认 5)、`minOrder`(默认 0)、`deliveryFee`、`minFree`；三端**删除硬编码 5**（现 5 处） |
| 配送费 | 真源收敛 | `goods = round2(Σ price×qty)`；`fee = (minFree>0 && goods>=minFree) ? 0 : deliveryFee`；`minFree<=0`=不免运费；未知配送方式按 delivery；未知 tier 归 retail；Web/小程序改为同用例的薄适配层 |
| 状态文案 | 归一 | `pending`→待备货 / `delivering`→配送中 / `ready`→待取货 / `done`→已完成 / `cancelled`→已取消；三端逐字相同，测试锁定 |
| 管理端鉴权 | 通道就绪 | 新增 `server/cmd/server/adminauth.go`：`ADMIN_PASSWORD` + HMAC 签名 HttpOnly/SameSite=Strict Cookie + `POST /api/admin/login` + `requireAdmin(next, allowStaff)` 逐路由包装；`ADMIN_PASSWORD` 未设置=放行并打 WARN（灰度开关，先发版后配置，避免锁死老板）；Cookie = `HttpOnly` + `SameSite=Strict` + `Path=/` + 7 天 `MaxAge`，签名 `HMAC-SHA256(ADMIN_PASSWORD, payload+过期时间戳)`，校验用 `hmac.Equal` 常量时间比较；公开端点保持 `/healthz`、`/api/admin/login|logout`、`/api/wx/*`、`/api/staff/*` |

### 7.2 `GET /api/products` 扩参（向后兼容，老调用方不传新参 = 行为不变）

| 参数 | 取值 | 默认 | 规则 |
|---|---|---|---|
| `keyword` | 字符串 | 空 | 不变：名称/品牌/条码模糊匹配 |
| `category` | 字符串 | 空 | 不变 |
| `onSale` | `1` | 空 | 不变：`1` 只回上架 |
| `phone` | 手机号 | 空 | 不变：算该顾客 `tier` 有效价 |
| `sort` | `default`/`hot`/`price_asc`/`price_desc`/`stock_desc` | `default` | 未知值 → **400** `排序方式不支持：<值>` |
| `limit` | 整数 | `0`（不限） | `>200` 按 `200` 处理；负数 → 400 |
| `offset` | 整数 | `0` | 负数 → 400 |

响应：`{"items":[…],"total":<过滤后总数>,"limit":<生效limit>,"offset":<生效offset>,"hasMore":<bool>,"tier":"retail"|…}`。
- **`total` 必须是过滤后的真实总数**（`COUNT(*)`），不是当前页条数——第 27 轮已把 `/api/orders` 修正过，商品这边同口径。
- **价格排序按顾客有效价排**：`tier!=retail && wholesale_price>0` 时用 `wholesale_price`，否则 `sale_price`（SQL 里 `CASE WHEN …`，不许先取出再在 Go 里排——否则分页会错）。
- `sort=hot` 口径：近 30 天 `status IN ('pending','delivering','ready','done')` 的订单明细 `SUM(qty)` 降序；**没销量的商品排在后面而不是被排除**；销量并列按 `on_sale DESC, name ASC`。
- `sort=default` = 现有顺序（保持第 27 轮行为，测试不许挂）。
- `sort=stock_desc` 按 `stock DESC`，并列 `name ASC`。

### 7.3 新增 `GET /api/products/hot?limit=8&phone=`

`{"items":[…],"total":…}`，口径同 `sort=hot`；`limit` 默认 8、最大 20。只回上架商品。首页「热销」与「无结果推荐」共用。

### 7.4 新增 `GET /api/products/alternatives?code=<缺货码>&limit=5`

`{"items":[…],"total":…}`。规则：`on_sale=1`、`stock>0`、排除自身；**优先同分类**按热销降序，同分类不足 `limit` 时用全店热销补足（不重复）。`code` 缺失/商品不存在 → `{"items":[],"total":0}`（不是 400，页面要能安静降级）。

**`total` 语义（第 28 轮定稿）**：`total` = **候选池总数**（已排除自身、缺货、下架），可以大于 `limit`，只有 `items` 截断到 `limit`。实现方曾按「`total` 就是返回条数」写用例夹具，导致 `alternatives` 断言候选数偏少；这里明确以「候选池总数」为准，页面只用 `items`。

### 7.5 `GET /api/orders` 筛选（管理端，与 R27 身份规则叠加）

新增参数（**都用新名字，绝不复用 `phone`**）：`q`（顾客名/手机号/订单号模糊）、`status`（逗号分隔多值，如 `pending,delivering`）、`date=YYYY-MM-DD`（本地日）、`from`/`to`（含端点的日期区间）、`type=pickup|delivery`。
- **`q` / `status` / `date` / `type` 只做筛选，不参与身份判定**；身份照第 27 轮（管理员 > 员工令牌 > openid > phone > 400）。
- **顾客身份下这些筛选只能在本人订单内再筛**（先归属过滤再筛选），管理员/员工才看全店。
- `date` 与 `from`/`to` 同时给 → `date` 优先。
- 非法日期 → 400 `日期格式应为 YYYY-MM-DD`。

### 7.6 新增 `GET /api/orders/export.csv`（带 BOM）

- 同一套筛选参数 + `limit`（默认 2000，最大 5000）。
- 响应头：`Content-Type: text/csv; charset=utf-8`、`Content-Disposition: attachment; filename="orders-YYYYMMDD-HHMM.csv"`。
- body **首三字节必须是 `EF BB BF`**（Excel 打开不乱码）。
- 列顺序（固定，共 12 列）：`订单号,下单时间,状态,顾客,手机号,配送方式,商品明细,件数,商品金额,配送费,合计,备注`。
- 明细列格式 `商品名×数量;`（多条拼接，末条也带 `;`）；金额保留 2 位；时间 `YYYY-MM-DD HH:MM:SS`。
- **RFC4180 转义**：字段含 `,`、`"`、`\n` 时用 `"` 包裹、内部 `"` 写成 `""`（顾客名/地址/备注真会出现这些字符）。
- 身份：走 `adminGate`（未配 `ADMIN_PASSWORD` = 灰度放行，与后台其他接口一致；配了则要管理员 Cookie）。**如实披露：灰度档下导出接口无身份也能调**，与 6.2 缺口同源，R30 一并收口。

### 7.7 索引（本轮**不新增任何列**，故不涉及第 30 条第⑩点的升级陷阱）

### 9.3 本轮发现的缺口（如实披露，留给后续轮）
- **灰度档鉴权缺口仍是最大的洞**：未设 `ADMIN_PASSWORD` 时无身份请求按管理端放行 —— `GET /api/orders` 无身份会返回全店订单（含顾客姓名/手机号），`export.csv` 无身份也能调。这是第 27 轮 §6.2 的同一处缺口，**必须与第 30 轮的 `#loginGate` 一起收口**。
- `requireAdmin` **不认员工令牌**：员工小程序的三条写路径（`POST /api/stock/change`、`POST /api/products`、`POST /api/products/onsale`）在开启 `ADMIN_PASSWORD` 后会被自己的鉴权挡住；修法已定（`requireAdmin(next, allowStaff)`），与后台登录页同轮交付。
- Web 商城端没有触摸下拉刷新手势（下拉刷新在小程序侧已做）；Web 触底加载依赖 `IntersectionObserver`，老浏览器自动降级为按钮。
